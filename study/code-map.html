10. Pipelining

הגדרה

במקום לשלוח REQUEST ולחכות ל-PIECE לפני הבא, אני שולח עד 50 בקשות פתוחות בו-זמנית לכל peer. תשובות מגיעות אסינכרונית, וכל PIECE שמגיע פותח מקום לבקשה חדשה. הצינור (TCP) תמיד מלא.

למה זה קריטי: TCP הוא bandwidth-delay product pipe. בלי pipelining, על RTT של 100ms ובלוקים של 16KB, ההורדה מוגבלת ל-160 KB/s. עם pipeline של 50 — 8 MB/s. פי 50.

החישוב שאני זורק לבוחן

RTT (round-trip) טיפוסי = 100ms
BLOCK_SIZE = 16 KB

ללא pipelining:
  block אחד לכל RTT
  → 16 KB / 0.1s = 160 KB/s   # bottleneck!

עם pipelining של 50:
  50 blocks לכל RTT
  → 50 × 16 KB / 0.1s = 8 MB/s   # פי 50

מה לומר בעל-פה

"Pipelining זה שאני לא מחכה ל-PIECE לפני שאני שולח REQUEST הבא. במקום, אני שומר ב-_pending_requests set של עד 50 בקשות פתוחות לכל peer. כל פעם שמגיע PIECE, אני מוציא את הבקשה מה-set ומיד שולח חדשה — כך הצינור תמיד מלא.

בלי זה, על RTT של 100ms הייתי מקבל רק 160 KB/s. עם pipeline של 50, אני מקבל 8 MB/s — פי 50. זה ההבדל בין לעבוד לבין לא לעבוד על קישור אמיתי."

הניתוחים שהבוחן ירצה לשמוע

Rarest-First — למה O(N) ולא יותר טוב?

for i in range(self.num_pieces):           # O(N)
    if status != MISSING: continue
    freq = self._peer_frequency.get(i, 0)   # O(1)
    if freq < min_freq: candidates = [i]
    elif freq == min_freq: candidates.append(i)
return random.choice(candidates)           # O(K), K ≤ N

שאלה אפשרית: "אפשר ב-O(log N) עם min-heap?"

תשובה: כן — heapq עם (freq, piece_idx). אבל יש 3 בעיות:
  1. Tie-breaking: ה-heap נותן אחד מ-min, לא את כל ה-min set. הייתי צריך לשלוף עד שה-freq עולה ולשמור bucket.
  2. Updates: כל BITFIELD/HAVE → O(log N) במקום O(1).
  3. N קטן: ל-N=4000, O(N) זה כ-4μs ב-Python. ה-constant factor של heap operations מבטל את היתרון.
עם זאת — לטורנט של 100GB (N=400,000) — הייתי שוקל heap.

Tit-for-Tat — מה אומר O(P log P · W)?

non_snubbed.sort(
    key=lambda x: x[1].bytes_received_in_window(20),  # O(W) per call
    reverse=True
)
  • Sort עצמו: O(P log P) comparisons
  • כל comparison: O(W) — קריאה ל-bytes_received_in_window
  • סה"כ: O(P · log P · W)

עם המספרים: P=50, W=30 → 50 × log(50) × 30 ≈ 9,000 פעולות. רץ כל 10s → זניח לחלוטין.

אופטימיזציה אפשרית: לעשות cache ל-bytes_received_in_window פעם אחת לפני ה-sort → O(P·W + P log P). לא עשיתי כי אין צורך.

Sliding Window — למה O(W) ולא O(1)?

def bytes_received_in_window(self, window=20.0):
    cutoff = time.time() - window
    total = 0
    for t, b in self._download_samples:    # O(W)
        if t >= cutoff:
            total += b
    return total

שאלה אפשרית: "אפשר O(1) עם running sum?"

תשובה: כן — לתחזק running_total שמתעדכן ב-append ו-eviction. הסיבה שלא עשיתי: W=30, וקריאות הן 50 peers × 1 לכל 10s = 5/sec. סה"כ 150 פעולות לשנייה — חסר משמעות.

BITFIELD update — O(N) הוא הצוואר בקבוק האמיתי

def update_peer_pieces(self, peer_key, pieces):
    for i in range(len(pieces)):           # O(N)
        if pieces[i]:
            self._peer_frequency[i] += 1     # O(1)

מתי זה רץ? פעם אחת לכל peer חדש שמתחבר. אם 200 peers מתחברים תוך דקה ול-N=10,000 → 2M פעולות = כ-200ms ב-Python. זה מורגש. זה הדבר היחיד שלא אופטמלתי, ואם הבוחן ישאל "מה היית משנה" — זו התשובה.

Broadcast HAVE — O(P) אבל concurrent

async def _broadcast_have(self, piece_index):
    tasks = [self._safe_send_have(conn, piece_index)
             for conn in self._connections.values()]
    await asyncio.gather(*tasks, return_exceptions=True)

P משימות נשלחות במקביל. Wall-clock time = O(max network latency), לא O(P × latency). זה הקסם של asyncio — concurrency בלי threads.

מה לומר בעל-פה (תבנית קצרה)

"רוב הפעולות החמות הן O(N) או O(1):

  • בחירת piece היא O(N) — סריקה לינארית של ה-pieces. אפשר O(log N) עם min-heap אבל ל-N=4000 זה לא מצדיק את המורכבות.
  • Tit-for-tat הוא O(P log P · W) כי יש sort, אבל P חסום ב-50, וזה רץ רק כל 10 שניות.
  • SHA-1 verification הוא O(K) על piece size — 256KB. כדי לא לחסום את ה-event loop, אני מריץ אותו ב-ThreadPoolExecutor.
  • send_request ו-HAVE update הם O(1) — הפעולות שרצות הכי הרבה.

זיכרון: הצורך הדומיננטי הוא blocks ב-flight — 50 peers × 50 pending × 16KB = 40MB. שאר המבנים זניחים."
