# פרק 8 – ניתוח חלופות מערכתי

## פתיח

פרק זה מבצע **ניתוח חלופות פורמלי** לפתרון הבעיה שהוגדרה בפרק 1
(הפצת קובץ גדול ביעילות, באמינות וברוחב פס מבוזר). בעוד שפרק 7
תיאר את הפתרונות הקיימים בעולם, פרק זה **שופט** ביניהם לפי
קריטריונים שיטתיים. השיפוט נעשה בשני מפלסים:

- **מפלס ארכיטקטוני** (8.1–8.5) — איזה ארכיטקטורה כללית בוחרים
  לפתרון הבעיה? Client-Server? P2P? היברידי?
- **מפלס מימוש** (8.6) — אם נבחר P2P (BitTorrent), כיצד לממש אותו?
  על בסיס ספרייה קיימת? מאפס בשפה אחת? מאפס בשתי שפות עם
  אינטגרציה?

לכל חלופה ניתנת **טבלת SWOT** (Strengths, Weaknesses, Opportunities,
Threats), בהתאם להנחיית המחוון לקטגוריה *"פתרון בעיה אלגוריתמית
בטכנולוגיות הנדסה מתקדמות"* (סעיף *"ביצוע SWOT לטכנולוגיות
אפשריות לפתרון"*). לאחר ניתוח החלופות, פרק 9 יציג את **ההצדקה
המלאה** לחלופה הנבחרת.

## 8.1 קריטריוני השיפוט

לפני הצגת החלופות, יש להגדיר את הקריטריונים שמולם תיבחן כל חלופה.
שמונה קריטריונים נבחרו, המבוססים על דרישות המחוון, על מטרות-העל
מפרק 3, ועל מאפייני הבעיה כפי שהוגדרה בפרק 1:

| קוד | קריטריון | שיוך למחוון / לפרויקט |
|---|---|---|
| **C1** | **סקלביליות** — יכולת המערכת לטפל במספר רב של משתמשים | מאפיין מהותי של הבעיה |
| **C2** | **עמידות לכשלים** — מה קורה כאשר רכיב נופל | רלוונטי ל-G4 בפרק 3 |
| **C3** | **עלות תפעולית** — כמה עולה להפעיל את הפתרון לאורך זמן | שיקול הנדסי כללי |
| **C4** | **מורכבות מימוש** — כמה זמן וידע נדרשים למימוש | שיקול פרקטי לפרויקט גמר |
| **C5** | **עמידה בדרישות המחוון** — שתי שפות, שפה מהודרת, ליבה אלגוריתמית, אינטגרציה, אבטחה | סעיפי המחוון (עיקרי) |
| **C6** | **ערך לימודי** — האם הפתרון מציג מורכבות שמדגימה ידע | משמעותי לפרויקט גמר |
| **C7** | **ביצועים** — תפוקה ויעילות שימוש ברוחב פס | רלוונטי ל-G1, G2 |
| **C8** | **שליטה ושקיפות** — האם מימוש הפתרון נמצא בידי המפתח, או נשען על קוד חיצוני | רלוונטי לסעיף 4 במחוון |

קריטריון C5 הוא הקריטי ביותר. כל חלופה שלא תעמוד בקריטריון זה
**אינה אפשרית** לבחירה, ללא תלות בציוניה האחרים.

## 8.2 חלופה א' — שרת HTTP/HTTPS מרכזי

### תיאור

מודל Client-Server קלאסי. שרת יחיד (או רשת קטנה של שרתים) מאחסן
את הקובץ ומגיש אותו ב-HTTP/HTTPS לבקשות לקוחות. הלקוח מבקש את
הקובץ, השרת מחזיר את הבייטים, וההורדה מסתיימת.

### ארכיטקטורה

```
[Client A] ─┐
[Client B] ─┼──→ [HTTP Server] ──→ [Disk Storage]
[Client C] ─┘
```

### טבלת SWOT — חלופה א'

| | Strengths | Weaknesses |
|---|---|---|
| **S/W** | פשטות מירבית בתכנון ובמימוש. אמינות תקשורת (TCP). תאימות אוניברסלית (כל דפדפן יודע HTTP). אבטחה סטנדרטית (TLS). | סקלביליות מוגבלת ע"י רוחב הפס של השרת. נקודת כשל יחידה. עלות תפעולית גבוהה למפיץ (השרת משלם על כל הבייטים). חוסר ניצול של רוחב פס בצד הלקוחות. |
| | **Opportunities** | **Threats** |
| **O/T** | הרחבה ל-CDN (חלופה ב'). שילוב עם cache layers (Redis, CDN edge). דחיסה ב-gzip/brotli. | התקפת DDoS משביתה את כל השירות. עלות גוברת אקספוננציאלית עם גידול הביקוש. תלות מוחלטת בשרידות השרת. |

### הערכה לפי הקריטריונים

| קריטריון | ציון | הערות |
|---|---|---|
| C1 — סקלביליות | **נמוך** | מוגבל ע"י השרת |
| C2 — עמידות | **נמוך** | נקודת כשל יחידה |
| C3 — עלות | **גבוה (שלילי)** | מפיץ נושא בכל העלות |
| C4 — מורכבות מימוש | **נמוך מאוד (חיובי)** | מאות שורות קוד |
| C5 — עמידה במחוון | **נכשל** | אין אלגוריתם בליבה; אין שתי שפות באופן טבעי; אין ליבה אלגוריתמית |
| C6 — ערך לימודי | **נמוך** | טכניקות הפצה בסיסיות |
| C7 — ביצועים | **תלוי בשרת** | יעיל כש-load נמוך |
| C8 — שליטה ושקיפות | **גבוה** | מימוש מלא בידי המפתח |

**מסקנה**: חלופה א' **נכשלת בקריטריון C5** ולכן אינה אפשרית
לפרויקט. גם בקריטריון C6 (ערך לימודי) היא מקצרת מאוד.

## 8.3 חלופה ב' — Content Delivery Network (CDN)

### תיאור

הרחבה של חלופה א'. שרת מקור יחיד + רשת של edge servers מבוזרת
גיאוגרפית. בקשות לקוחות מנותבות אוטומטית ל-edge הקרוב, באמצעות
DNS-based routing או Anycast.

### ארכיטקטורה

```
                     ┌── [Edge US-East]
[Origin Server] ─────┼── [Edge EU-West]    ─── ─→ [Clients]
                     └── [Edge Asia-Pacific]
```

### טבלת SWOT — חלופה ב'

| | Strengths | Weaknesses |
|---|---|---|
| **S/W** | סקלביליות גבוהה. השהיה נמוכה (קרוב למשתמש). עמידות לכשלים (edges מרובים). מקובל ומוכר בתעשייה. | עלות מסחרית גבוהה (שירותי CDN בתשלום). תלות בספק (vendor lock-in). אינו "מבוזר אמיתית" (יש בעלים). עדיין נקודת כשל יחידה ברמת ה-origin. |
| | **Opportunities** | **Threats** |
| **O/T** | שילוב עם תחזוקה דינמית (CloudFlare Workers). הרחבה ל-multi-CDN. | התקפת DDoS גדולה מספיק יכולה להפיל גם CDN. שינוי תמחור של ספק. צנזורה ע"י ספק. |

### הערכה לפי הקריטריונים

| קריטריון | ציון | הערות |
|---|---|---|
| C1 — סקלביליות | **גבוה** | מצוין |
| C2 — עמידות | **גבוה** | edges מרובים |
| C3 — עלות | **גבוה (שלילי)** | תשלום לספק CDN |
| C4 — מורכבות מימוש | **נמוך (חיובי)** | "תזרמים פנימה" — הספק עושה את העבודה |
| C5 — עמידה במחוון | **נכשל לחלוטין** | המפתח אינו מממש שום ליבה; הפרויקט יהיה "קונפיגורציה" של ספק חיצוני |
| C6 — ערך לימודי | **נמוך מאוד** | אין למידה משמעותית |
| C7 — ביצועים | **גבוה** | מצוין |
| C8 — שליטה ושקיפות | **אפסי** | הכל אצל הספק |

**מסקנה**: חלופה ב' **נכשלת בקריטריונים C5, C6, C8**. היא יעילה
מסחרית אך אינה רלוונטית לפרויקט גמר לימודי-יישומי.

## 8.4 חלופה ג' — P2P מבוזר (BitTorrent)

### תיאור

מודל Peer-to-Peer מלא לפי פרוטוקול BitTorrent (BEP-3). אין שרת
מרכזי המחזיק את הקובץ; הקובץ מפוזר בין peers שהם בו-זמנית מורידים
ומפיצים. שרת מתאם קל-משקל (tracker) מספק רשימת peers לזרים
חדשים. אלגוריתמי rarest-first ו-Tit-for-Tat מבטיחים יעילות
ועמידות.

### ארכיטקטורה

```
                 ┌── [Peer A] ──┐
[Tracker] ─────┬─┤              ├── (data flows directly)
               └─┤    Swarm     │
                 └── [Peer B] ──┘
                 └── [Peer C] ──┘
```

### טבלת SWOT — חלופה ג'

| | Strengths | Weaknesses |
|---|---|---|
| **S/W** | סקלביליות לינארית — ככל שיותר peers, יותר רוחב פס. עמידות גבוהה (אין שרת תוכן). עלות נמוכה למפיץ (רק tracker). אלגוריתמיקה עשירה ומעניינת לימודית. | מורכבות מימוש גבוהה. בעיות חיבור מאחורי NAT. תלות במספר peers ב-swarm (torrent "מת" עם 0 seeders). תוכן מלוכלך/לא חוקי משויך לפרוטוקול במוצרים מסחריים. |
| | **Opportunities** | **Threats** |
| **O/T** | הרחבה ל-DHT לחיסול תלות ב-tracker. שילוב עם blockchain (כמו Filecoin) לתמרוץ. שימוש בעולם הארגוני (Twitter Murder, Facebook Wormhole). | עוסקי תוכן (ISPs) חוסמים את הפרוטוקול. peers זדוניים. רגולציה. שינויים בפרוטוקול v1 → v2 דורשים עדכון. |

### הערכה לפי הקריטריונים

| קריטריון | ציון | הערות |
|---|---|---|
| C1 — סקלביליות | **גבוה מאוד** | לינארית ב-peers |
| C2 — עמידות | **גבוה** | אין נקודת כשל יחידה |
| C3 — עלות | **נמוך (חיובי)** | רק tracker; אפילו אפשר ללא |
| C4 — מורכבות מימוש | **גבוה (אתגר)** | פרוטוקול עשיר, אלגוריתמיקה |
| C5 — עמידה במחוון | **גבוה** | יש ליבה אלגוריתמית מהותית, תאימות מובנית להפרדה רב-לשונית |
| C6 — ערך לימודי | **גבוה מאוד** | מקיף שכבות OS, רשתות, אלגוריתמיקה, אבטחה |
| C7 — ביצועים | **גבוה** | יעיל ב-swarm פעיל |
| C8 — שליטה ושקיפות | **גבוה** | מימוש בידי המפתח |

**מסקנה**: חלופה ג' **עומדת בכל הקריטריונים** וזוכה לציון גבוה
ברוב הקטגוריות. היא **המועמדת המובילה** לפתרון. הקריטריון היחיד
שבו היא "חלשה" הוא C4 (מורכבות מימוש), אך זוהי דווקא **תכונה
חיובית** בהקשר של פרויקט גמר — היא מאתגרת ויוצרת הזדמנות
להוכחת מסוגלות.

## 8.5 חלופה ד' — Content-Addressed P2P מודרני (IPFS)

### תיאור

פרדיגמה מודרנית יותר של P2P, שבה כל קובץ מזוהה ב-Content
Identifier (CID) המבוסס על hash שלו. במקום swarm נפרד לכל torrent,
IPFS הוא רשת אחת גלובלית. החיפוש מתבצע ב-DHT (Kademlia-based),
והעברת הבלוקים בפרוטוקול BitSwap.

### ארכיטקטורה

```
[Node 1] ←─ DHT lookup ─→ [Node 2]
   │           ↕             │
   └────── BitSwap ──────────┘
   ↕           ↕             ↕
[Local Blockstore]   (Content-addressed)
```

### טבלת SWOT — חלופה ד'

| | Strengths | Weaknesses |
|---|---|---|
| **S/W** | רשת אחת גלובלית — אין צורך בקבצי torrent נפרדים. עמידות גבוהה במיוחד. תמיכה ב-versioning דרך IPNS. אינטגרציה עם blockchain (Filecoin). | פרוטוקול מורכב יותר מ-BitTorrent. ספרות אקדמית פחות בוגרת (גיל יחסי). אימוץ מצומצם מחוץ לקהילת Web3. ה-go-ipfs (kubo) מתחזק, ה-js-ipfs פחות. |
| | **Opportunities** | **Threats** |
| **O/T** | עידן Web3 מעודד אימוץ. שילוב עם NFTs ו-decentralized storage. | תלות באקוסיסטם blockchain שלא תמיד יציב כלכלית. רגולציה על Web3 ו-crypto. |

### הערכה לפי הקריטריונים

| קריטריון | ציון | הערות |
|---|---|---|
| C1 — סקלביליות | **גבוה מאוד** | רשת גלובלית |
| C2 — עמידות | **גבוה מאוד** | אין tracker יחיד |
| C3 — עלות | **נמוך (חיובי)** | פתוח |
| C4 — מורכבות מימוש | **גבוה מאוד** | יותר מ-BitTorrent |
| C5 — עמידה במחוון | **גבוה** | ליבה אלגוריתמית עשירה |
| C6 — ערך לימודי | **גבוה מאוד** | אך פחות מבוסס באקדמיה מ-BitTorrent |
| C7 — ביצועים | **בינוני** | עדיין בשלב פיתוח |
| C8 — שליטה ושקיפות | **גבוה** | קוד פתוח |

**מסקנה**: חלופה ד' **קרובה לחלופה ג'** בציוניה, אך מציבה
**חסם פרקטי**: כמות הספרות והמקורות הזמינים על BitTorrent (הסטנדרטי,
המבוסס) גבוהה משמעותית, ולכן הסיכוי להצלחה בלוח זמנים של פרויקט
גמר גבוה יותר עם BitTorrent. בנוסף, BitTorrent נכלל בתוכנית הלימודים
של י"ג/י"ד כפרוטוקול-יישום מרכזי של P2P.

## 8.6 ניתוח חלופות מימוש (בהינתן בחירת BitTorrent)

לאחר ההכרעה הראשונית לטובת BitTorrent (חלופה ג'), נדרש ניתוח
**שכבת המימוש**: כיצד לממש את BitTorrent בפועל?

### חלופה ג'.1 — שימוש בספריית BitTorrent קיימת (libtorrent)

**תיאור**: הפרויקט יהיה GUI שעוטף את libtorrent-rasterbar. הליבה
האלגוריתמית מסופקת ע"י הספרייה; המפתח כותב רק GUI ומעטפת.

### טבלת SWOT — חלופה ג'.1

| | Strengths | Weaknesses |
|---|---|---|
| **S/W** | מהירות מימוש גבוהה. אמינות הוכחה. תמיכה בכל הרחבות BitTorrent. | אין למידה משמעותית של הפרוטוקול. תלות בקוד חיצוני. הפרויקט הופך ל"qBittorrent מינימליסטי". |
| | **Opportunities** | **Threats** |
| **O/T** | יכולת להוסיף פיצ'רים מתקדמים מהר. | **נכשל בסעיף 4 במחוון** (*"אם הפרויקט כולו מורכב מ-API אחד לפתרון ליבת הבעיה ללא אינטגרציה — זוהי עילה למתן ציון נכשל"*). |

**ציון C5**: **נכשל לחלוטין**. החלופה הזו **פסולה**.

### חלופה ג'.2 — מימוש מאפס בשפה אחת (Python בלבד)

**תיאור**: כל הפרויקט ב-Python — מנוע BitTorrent + CLI / TUI. אין
GUI נפרד.

### טבלת SWOT — חלופה ג'.2

| | Strengths | Weaknesses |
|---|---|---|
| **S/W** | מימוש מלא של הליבה האלגוריתמית. שפת פיתוח מהירה (Python). | חוסר עמידה בסעיף 8 במחוון — דורש שתי שפות עם אינטגרציה, או לפחות שפה מהודרת אחת. Python אינה מהודרת. |
| | **Opportunities** | **Threats** |
| **O/T** | קוד פשוט יותר לקריאה ולתחזוקה. | **נכשל בסעיף 8 במחוון**. |

**ציון C5**: **נכשל**. החלופה הזו **פסולה**.

### חלופה ג'.3 — מימוש מאפס בשתי שפות עם אינטגרציה (Python + Java)

**תיאור**: מנוע BitTorrent ב-Python (מאפס) + GUI ב-Java Swing
(שפה מהודרת) + אינטגרציה דרך REST API מקומי.

### טבלת SWOT — חלופה ג'.3

| | Strengths | Weaknesses |
|---|---|---|
| **S/W** | עומד בכל דרישות המחוון: שתי שפות, שפה מהודרת, אינטגרציה פונקציונלית, ליבה אלגוריתמית מאפס. הפרדת תהליכים שמדמה ארכיטקטורת ייצור (כמו Deluge, Transmission). חוויית למידה רחבה (שתי שפות, REST, threading). | מורכבות גבוהה מאוד. תיאום בין שתי שפות מציב אתגרים נוספים (קידוד, סנכרון). זמן פיתוח ארוך יותר. |
| | **Opportunities** | **Threats** |
| **O/T** | אפשרות להחליף את ה-GUI בלי לפגוע במנוע. אפשרות לחשוף את ה-API לכלי-צד-שלישי. | חוסר תיאום בין השפות יוצר באגים מורכבים (כמו באג ה-Stalling). שגיאות סדרון JSON בין השפות. |

**ציון C5**: **גבוה** — עומד בכל דרישות המחוון.

## 8.8 סיכום וגישור לפרק 9

הניתוח חשף תהליך שיפוט תלת-שלבי:

**שלב 1 — שיפוט ארכיטקטורות**. חלופות א' (HTTP) ו-ב' (CDN) נפסלו
בקריטריון C5 (עמידה במחוון) כי הן אינן מציעות ליבה אלגוריתמית
משמעותית. חלופות ג' (BitTorrent) ו-ד' (IPFS) שתיהן עומדות
בקריטריונים, אך BitTorrent בעל יתרון פרקטי בזכות בשלות, ספרות
ענפה ושייכות לתוכנית הלימודים.

**שלב 2 — שיפוט מימושים**. בתוך BitTorrent, חלופה ג'.1 (libtorrent)
נפסלה בקריטריון C5 (סעיף 4 במחוון — אסור API לליבה). חלופה ג'.2
(Python pure) נפסלה בקריטריון C5 (סעיף 8 — שתי שפות / שפה מהודרת
חובה). נותרה חלופה ג'.3 — **BitTorrent דו-לשוני (Python+Java) עם
REST API**.

**שלב 3 — הכרעה סופית**. חלופה ג'.3 היא היחידה העומדת בכל
הקריטריונים. היא תוצג בפירוט מלא בפרק 9 (תיאור החלופה הנבחרת),
על כל היתרונות, ההצדקות וההכרעות הסופיות.
