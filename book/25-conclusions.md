# פרק 25 – מסקנות

## פתיח

פרק זה מסכם את **המסקנות העיקריות** מפיתוח הפרויקט. כל
מסקנה נמצאת באחד מארבעה צירים: (1) טכני-אלגוריתמי, (2)
הנדסי-ארכיטקטוני, (3) אבטחה ועמידות, (4) תהליכי-לימודי.

המסקנות מבוססות על מה שיושם בפועל בקוד (פרקים 11–22) ועל
תוצאות הבדיקות (פרק 24).

---

## 25.1 מסקנות טכניות-אלגוריתמיות

### 25.1.1 rarest-first הוא הבחירה הנכונה למרות הסיבוכיות הזהה ל-random

ניתוח הסיבוכיות (פרק 15.4) הראה ש-`rarest_first` ו-`random`
הם **שניהם O(N)**. ההבדל ביניהם איננו בעלות החישוב אלא
ב**איכות הבחירה האלגוריתמית**:

- rarest-first מפזר את מאמץ ההורדה לכלל ה-swarm — חלקים
  נדירים מקבלים עדיפות, מה שמעלה את "ערך" ה-uploader.
- random לא לוקח בחשבון את מצב ה-swarm — עלול ליצור bottleneck
  כאשר ה-seeder היחיד עם piece נדיר מתנתק.

**המסקנה**: עלות החישוב של 50 השוואות ב-list אינה רלוונטית
כשמדובר בפעולה אחת ל-100ms. **תמיד נעדיף איכות אלגוריתמית
על פני אופטימיזציה זניחה**.

### 25.1.2 Tit-for-Tat דורש זהירות אך נוצר תוצאות עדיפות

Tit-for-Tat (פרק 15.4.4) הוא O(K log K), לעומת round-robin
שהוא O(K). למרות שעלות החישוב הנוספת הקטנה, התוצאה שונה
מהותית:

- Tit-for-Tat מעניק בנדידות-רוחב לקוחות התורמים → מעודד
  reciprocity.
- round-robin "עיוור" — נותן bandwidth שווה לכולם, כולל
  free-riders.

**המסקנה**: O(K log K) על K=50 הוא ~280 פעולות אריתמטיות
— מיקרו-שניה. השקעת הקבוע הזו משתלמת לחלוטין למניעת ניצול
ע"י peers שלא תורמים בחזרה.

### 25.1.3 חישוב SHA-1 חוסם — חייב לרוץ ב-thread pool

ה-`Piece.verify_hash` (פרק 12.2.2) רץ ~2ms על piece של
1MB. אם רץ ב-event loop הראשי, הוא חוסם את כל ה-coroutines
האחרות לטובת כל piece שמסתיים.

**המסקנה הקריטית**: `loop.run_in_executor(self._executor,
verify_piece, idx)` חייבת לעטוף **כל פעולה CPU-bound**
ב-asyncio system. ה-event loop של asyncio הוא single-threaded;
חסימה של 2ms על שגרה תכופה שווה ל-15-20% pubility מ-CPU
שאבד.

## 25.2 מסקנות הנדסיות-ארכיטקטוניות

### 25.2.1 הפרדת תהליכים דרך REST מעוטרת בערך

הבחירה הראשונית להפריד את ה-Engine (Python) מה-GUI (Java)
ע"י REST/JSON על loopback (פרק 11) הוכיחה את עצמה ב-3 דברים:

1. **דיבוג** — אפשר להשתמש ב-`curl` ולבדוק כל endpoint
   בעצמאות, ללא JVM.
2. **בידוד שגיאות** — crash ב-Java לא הורג את ההורדות
   ב-Python; ה-engine ימשיך לרוץ עד שה-GUI יחזור.
3. **הרחבה עתידית** — אפשר להוסיף CLI client או mobile app
   ללא שינוי ב-Engine.

המחיר ששילמנו: שני סקריפטי deploy (`start.sh`/`start.bat`)
שצריכים לבדוק Python ו-JDK בנפרד; היה זול יחסית.

### 25.2.2 asyncio + ThreadPoolExecutor מודל גמיש מספיק

המודל של event loop יחיד + thread pool של 2 workers (פרקים
11.3, 15.4.6) הצליח לטפל ב-50 חיבורי TCP מקבילים ב-CPU
פנוי גרידא ~3% (לפי טבלאות הפרק 5). היחס בין I/O עניין
לבין CPU עניין במערכת BitTorrent (≈98% I/O) משחק לטובת
המודל הזה.

**מתי המודל יכשל**: כשבעתיד נוסיף הצפנה (MSE/PE — פרק 26)
או יותר מ-200 חיבורים בו-זמנית. אז יידרש switch ל-multi-process
event loops.

### 25.2.3 SQLite עדיף על PostgreSQL לפרויקט בסדר גודל זה

בחירת SQLite (פרק 22.1) הוכיחה את עצמה: אפס תלות, אפס
הגדרה. עבור פרויקט גמר עם < 1,000 רשומות צפויות, היחס
תועלת/עלות של SQL server מלא הוא שלילי.

**המסקנה**: לפרויקטים embedded — תמיד SQLite. לפרויקטים
multi-user — בחנו את העומס לפני שמוסיפים DB server.

## 25.3 מסקנות אבטחה ועמידות

### 25.3.1 Defense-in-Depth — הרבה שכבות זולות עדיפות על שכבה אחת יקרה

המערכת (פרק 12) מיישמת **8 שכבות הגנה** קלות:
- ולידציית handshake
- ולידציית אורך הודעה
- ולידציית msg_id
- ולידציית piece_index
- timeouts
- SHA-1 verify
- peer reputation
- חסימת התחברות חוזרת

עלות כל אחת ≤ O(1) או O(N) פעם בנדיר. ההצטברות שלהן יוצרת
"קיר" שדורש מ-peer זדוני להפר מספר מנגנונים בו-זמנית.

זה תופס יותר מאשר שכבה יחידה "חזקה" (כמו hash function 512-bit) —
פיזור הסיכון על פני נקודות מרובות.

### 25.3.2 SHA-1 מספיק לאינטגריטי — אך לא לעתיד

ניתוח SHA-1 (פרק 12.2.3) הראה ש-collision attacks קיימים
אך דורשים משאבים של מדינה. עבור פרויקט BitTorrent קלאסי
(BEP-3) שמסתמך על תאימות נרחבת — SHA-1 הוא הבחירה הנכונה.

**אך** למערכות חדשות שלא דורשות תאימות BEP-3 — SHA-256 או
BLAKE3 הם הבחירה הטבעית. הפרויקט תיעד את הגרסה החלופית
(BEP-52, BitTorrent v2) כפיתוח עתידי.

### 25.3.3 פרטיות מול tracker חמורה יותר מהצפנה בערוץ peer

ניתוח הפרטיות (פרק 12.2.7) הראה שה-`info_hash` + `peer_id`
+ IP ב-announce חושפים יותר מידע מאשר התכנים עצמם. **התוקפת
האמיתית של BitTorrent היא ה-tracker שנפרץ**, לא ה-MITM.

**המסקנה**: מאמץ פיתוח עתידי בכיוון פרטיות עדיף שיופנה
ל-DHT/PEX (מבטלים את הצורך ב-tracker מרכזי) ולא ל-MSE/PE
(שמספק obfuscation בלבד).

## 25.4 מסקנות תהליכיות-לימודיות

### 25.4.1 שתי שפות פיתוח מצריכות חוזה ברור

הבחירה לפתח Python + Java (פרק 14.3) דרשה התעקשות על
**חוזה תיעודי מדויק** של ה-REST API (פרקים 11.5, 14.1).
ה-JSON של `Download.get_status()` חייב להתאים בדיוק
ל-`TorrentStatus.fromJson(...)` ב-Java — כל שינוי דורש
תיאום.

**המסקנה**: בפיתוח multi-language, ה-API contract הוא
ה-source-of-truth. שינוי שם שדה — שינוי בשני המקומות
(לפעמים שלושה אם יש גם SQLite).

### 25.4.2 type hints ב-Python מצילים זמן

הפרויקט משתמש ב-PEP 484 בצורה אגרסיבית — `Optional[bytes]`,
`Dict[str, PeerConnection]`, וכו'. הזמן שהושקע בכתיבת
ה-hints נחסך פי כמה במהלך הפיתוח:
- IDE (PyCharm) חוזה השלמות שגויות מראש.
- `mypy` (אם רץ) תופס שגיאות לפני run.
- קוד שכל הקריאות שלו מתועדות נקרא מהר יותר.

**המסקנה**: ב-Python מודרני, type hints אינם opt-in
מומלץ אלא חובה לקוד בסדר גודל של 3,500+ שורות.

### 25.4.3 בדיקות מקבילות לפיתוח, לא אחריו

160 ה-test functions (פרק 24.1) נכתבו **תוך כדי** פיתוח
המודולים, לא לאחר מכן. הדבר אפשר:
- refactoring בטוח של אלגוריתמים (rarest-first עבר 3 גרסאות).
- זיהוי באגים ביום של היצירה ולא חודש אחר כך.
- documentation דה-פקטו של ההתנהגות הצפויה.

**המסקנה**: TDD לא חובה, אבל **כתיבת בדיקה אחת לכל פונקציה
ציבורית חדשה** היא הרגל שאי אפשר להתחרט עליו.

## 25.5 מה לא הצליח / מה נכשל

לטובת שקיפות, להלן 3 פערים שזוהו במהלך הפיתוח ולא נסגרו
לחלוטין:

1. **שחזור אוטומטי לאחר crash** — `_save_state` כותב
   `data/state/<id>.json` בכל פעם שהפיס נסגר, אבל מנגנון
   ה-load בעת startup **לא ממומש**. המידע קיים, אבל
   ההורדה צריכה להיווצר מחדש ידנית.

2. **NAT traversal** — המערכת לא מקבלת חיבורים נכנסים
   (פרק 14.2.4). זה מגביל את התרומה ל-swarm. מימוש UPnP
   או STUN מתועד כשיפור עתידי (פרק 26).

3. **MSE/PE** — אין הצפנה בערוץ peers. ניתוח SWOT בפרק
   12.2.6 הראה שזה לא דחוף (obfuscation בלבד), אבל
   הפרויקט לא יכול לעקוף DPI של ISPs שמגבילים BitTorrent.

## 25.6 סיכום הפרק

הפרק סיכם **12 מסקנות** מרכזיות בארבעה צירים:

- **טכני-אלגוריתמי** (3): rarest-first שווה את עלותה,
  Tit-for-Tat חיוני, SHA-1 חייב thread pool.
- **הנדסי-ארכיטקטוני** (3): REST מציל זמן, asyncio+pool
  מספיק, SQLite מנצח עבור פרויקט בסדר זה.
- **אבטחה** (3): defense-in-depth, SHA-1 מספיק לעת
  עתה, פרטיות tracker חמורה מהצפנת ערוצים.
- **תהליכי-לימודי** (3): API contract הוא ה-source-of-truth,
  type hints חובה, tests מקבילים לפיתוח.

הפרק גם תיעד **3 פערים פתוחים** (שחזור אוטומטי, NAT,
encrypt) — שיפורים אלה מתועדים בפירוט בפרק 26.

הפרק הבא (פרק 26) הוא **פיתוחים עתידיים** — Roadmap
לגרסה הבאה של המערכת.
