# פרק 9 – תיאור החלופה הנבחרת

## פתיח

פרק זה מציג את **החלופה הנבחרת** באופן רשמי ומלא. בעוד שפרק 8
ביצע ניתוח חלופות פורמלי שהוביל לפסילת שש חלופות וזיהוי של חלופה
אחת בלבד כעומדת בכל הקריטריונים, פרק זה מתעמק ב**מאפייני** החלופה
הנבחרת, ב**הצדקת** הבחירה, ב**ניהול הסיכונים** הכרוכים בה,
וב**הצדקת הבחירות התת-טכנולוגיות** שבתוכה — בחירת השפות הספציפיות,
פרוטוקול האינטגרציה ועקרונות התכן המרכזיים.

הפרק קצר ביחס לפרק הקודם: רוב העבודה האנליטית כבר נעשתה, ונותרה
**הפורמליזציה** של ההכרעה. עם זאת, חשיבותו של הפרק היא קריטית —
הוא **חוזה ההצדקה** מול הבוחנים בכל שאלה של *"למה בחרת בזה ולא
אחרת?"*.

## 9.1 הצגה רשמית של החלופה הנבחרת

**שם החלופה**: "מערכת שיתוף קבצים מבוזרת בסגנון BitTorrent —
מימוש מאפס בארכיטקטורת שתי שפות"

**תיאור תמציתי**: מערכת תוכנה הבנויה משני תהליכים נפרדים: מנוע
BitTorrent כתוב **ב-Python** המממש את פרוטוקול BEP-3 ואת אלגוריתמי
ה-rarest-first ו-Tit-for-Tat מבחינת מבנה האפליקציה; וממשק משתמש
גרפי כתוב **ב-Java Swing**. שני התהליכים מתקשרים ביניהם באמצעות
**REST API מקומי** הרץ על Flask ב-`localhost:5000`.

**מבנה מפורט**:

```
┌─────────────────────────────────────┐
│   Java GUI (Process 1, JVM)         │
│   ┌──────────────────────────────┐  │
│   │  TorrentClientGUI            │  │
│   │  + ApiService (HttpClient)   │  │
│   │  + AlgorithmStatsDialog      │  │
│   └──────────────────────────────┘  │
└───────────────┬─────────────────────┘
                │ REST/JSON over HTTP
                │ localhost:5000
                ▼
┌─────────────────────────────────────┐
│   Python Engine (Process 2)         │
│   ┌──────────────────────────────┐  │
│   │  Flask REST API Server       │  │
│   │  + Background asyncio loop   │  │
│   │  + DownloadManager           │  │
│   │  + PieceManager (rarest-first)│ │
│   │  + PeerConnection* (TCP)     │  │
│   │  + TrackerClient (HTTP)      │  │
│   │  + SecurityManager           │  │
│   │  + JSON state + SQLite       │  │
│   └──────────────────────────────┘  │
└─────────────────────────────────────┘
                │ TCP (BEP-3)
                │ HTTP (announce)
                ▼
        [Trackers + Peers in Swarm]
```

**שייכות לקטגוריות במחוון**: **בעיקר** *"מערכות הפעלה / רשתות
מחשבים / תקשורת נתונים / אבטחת מידע"*, ו**במשני** *"פתרון בעיה
אלגוריתמית בטכנולוגיות הנדסה מתקדמות"*.

### 9.2.2 עמידה בקריטריונים האחרים

- **C1 — סקלביליות**: P2P מספק סקלביליות לינארית ב-peers. נמדד

- **C2 — עמידות**: שני תהליכים נפרדים, כשל בצד אחד לא מקרין על
  השני. בנוסף, ה-engine שורד עזיבת peers ומחבר חיבורים מחדש.
- **C3 — עלות**: אפסית — תוכנת Desktop, ללא תלות בשירות.
- **C4 — מורכבות**: גבוהה, אך מנוהלת ע"י מודולריות והפרדת שכבות.
- **C6 — ערך לימודי**: הגבוה ביותר מבין החלופות.
- **C7 — ביצועים**: יעיל; הוכחה אמפירית תופיע בפרק 24.
- **C8 — שליטה ושקיפות**: 100% מהקוד נכתב בידי הסטודנט.

## 9.3 יתרונות מרכזיים של החלופה

### 9.3.1 יתרון 1 — הפרדת תהליכים אמיתית

הארכיטקטורה דו-תהליכית מספקת יתרונות אמיתיים, לא רק "תאימות
למחוון":

- **בידוד שגיאות**: כשל ב-GUI (NullPointerException, מחסור בזיכרון
  של Swing) אינו מפיל את המנוע, ולהפך. הורדות ממשיכות לרוץ גם
  כש-GUI סגור.
- **שדרוג עצמאי**: ניתן לעדכן את המנוע מבלי לעדכן את ה-GUI ולהפך
  (כל עוד ה-API שומר על תאימות).
- **יכולת לחשוף את ה-API**: כלי-צד-שלישי (CLI, סקריפטים אוטומטיים,
  אפילו GUI חלופי) יכולים להשתמש באותו מנוע.
- **דיבוג נפרד**: ניתן לבדוק את המנוע ב-pytest, ואת ה-GUI דרך
  Swing's event tester, מבלי שהם תלויים זה בזה.

### 9.3.2 יתרון 2 — מימוש מאפס מעמיק

מימוש מאפס של פרוטוקול BEP-3 משיג שלוש מטרות:

- **שליטה הוכחתית**: לא ניתן להעתיק ספרייה ולקרוא לזה פרויקט.
- **גמישות עתידית**: ניתן להוסיף הרחבות (DHT, PEX) מבלי להיתקל
  במגבלות API חיצוני.
- **תובנה לבעיות**: באג ה-Stalling התגלה ונפתר רק משום שהקוד היה
  "תחת השליטה" של המפתח — בלי גישה לקוד, לא ניתן היה לאתר את
  השורש.

### 9.3.3 יתרון 3 — מערכת מדידה מובנית

הפרויקט מציע **בנייה מובנית** של מערכת ניטור והשוואה
אלגוריתמית — דרך ה-endpoint `/algorithm-stats/<id>` וה-GUI dialog
`AlgorithmStatsDialog`. תכונה זו חורגת ממה שיש בלקוחות מסחריים
טיפוסיים, ומאפשרת **השוואת חלופות במציאות** ולא רק תיאורטית.

### 9.3.4 יתרון 4 — תיעוד הנדסי מקיף

המבנה הדו-תהליכי, יחד עם הצורך באינטגרציה ביניהם, חייב **תיעוד
פורמלי** של ה-API. זה הופך את הפרויקט ל**ניתן ללימוד מאחרים** —
תכונה לימודית חשובה. README, CURRENT_STATE.md, וספר הפרויקט יחד
מהווים תיעוד שקצב המקובל בלקוחות מסחריים.

## 9.4 ניהול סיכונים

בחירת חלופה ג'.3 כרוכה ב**סיכונים** שזוהו וטופלו. כל סיכון מוצג
עם **אופן ההתמודדות** שננקט בפרויקט:

### 9.4.1 סיכון: מורכבות סנכרון Python ↔ Java

**איום**: שני תהליכים נפרדים בשפות שונות מצריכים סדרון/פענוח
זהירים. שגיאה תוביל לבאגים מסתוריים.

**התמודדות**:

- שימוש ב-**JSON** כפורמט אחיד, עם libraries בוגרות בשני הצדדים
  (`json` ב-Python, `org.json` ב-Java).
- שימוש ב-**multipart/form-data** להעלאת בייטים בינאריים — לא
  base64 ב-JSON.
- **API חוזית**: כל שדה ב-JSON מתועד; שינויים בחוזה דורשים עדכון
  בשני הצדדים.
- **בדיקות אינטגרציה**: `test_api_server.py` בודק את כל ה-endpoints,
  ובדיקות ידניות מקצה-לקצה.

### 9.4.2 סיכון: התקעות בגלל threading שגוי

**איום**: Flask thread + asyncio event loop + ThreadPoolExecutor —
תרכובת מסוכנת לרייסים, deadlocks, ו-data corruption.

**התמודדות**:

- **חוקי ברזל**: כל קריאה חוצה-thread עוברת דרך
  `asyncio.run_coroutine_threadsafe()` עם `timeout=60` מוגדר.
- **אין משאבים משותפים בין threads**: המידע ב-`DownloadManager`
  נגיש רק ב-event loop. Flask thread *מבקש* פעולה, לא נוגע בה.
- **בדיקות עומס**: הרצת המערכת עם 50 peers במקביל וניטור CPU.

### 9.4.3 סיכון: זמן פיתוח ארוך

**איום**: מימוש שתי שפות וחיבור ביניהן מאריך את זמן הפיתוח לעומת
שפה אחת.

**התמודדות**:

- **לוח זמנים מובנה** (פרק 1.14): שלבים נפרדים למנוע, ל-API
  ול-GUI. המנוע נבנה תחילה ונבדק עם CLI לפני התחלת ה-GUI.
- **שימוש בכלים בוגרים**: Flask, Java Swing הם framework-ים
  בוגרים — אין צורך לבנות תשתית בסיסית.
- **קוד פשוט בכל שכבה**: GUI ב-Java אינו עושה לוגיקה — רק מציג
  ושולח בקשות.

### 9.4.4 סיכון: תקלות רשת מורכבות

**איום**: BitTorrent על peers אמיתיים מציג תקלות מציאותיות
(ניתוקים, peers זדוניים, NAT) שקשה לדמות בפיתוח.

**התמודדות**:

- **בדיקות יחידה** עם mock peers ב-`test_peer_connection.py`.
- **timeouts מובנים** בכל הרבדים.
- **לוגים מפורטים** באמצעות `_log_buffer` שמקלים על אבחון בהמשך.
- **מודול אבטחה** (`security.py`) שמתעד הפרות ומגן אוטומטית.

### 9.4.5 סיכון: באג ה-Stalling (כבר התרחש ונפתר)

**איום**: באג קריטי שיכול לסכל את הפרויקט. תועד בפרק 4.5.

**התמודדות**: כבר התרחש ונפתר. הפתרון הארכיטקטוני שתואר בפרק 4
הוא **תוצר חיובי** של הסיכון — הוא ייצב את הקוד הרבה מעבר למה
שהיה לפני הבאג.

## 9.5 הצדקת בחירת שפות הפיתוח

### 9.5.1 למה Python במנוע?

Python נבחרה למנוע BitTorrent מסיבות מצטברות:

1. **asyncio מובנה**: Python מספקת תמיכה native ב-asyncio ב-stdlib,
   ללא תלות חיצונית. asyncio הוא הכלי הנכון לאפליקציות עם עשרות
   חיבורי TCP במקביל (כפי שנדון בפרק 4.3.1).
2. **גמישות בטיפוסים בינאריים**: `bytes` ו-`bytearray` של Python
   מאפשרים מניפולציה ישירה של זרמי בייטים, כפי שנדרש ב-Bencode
   ו-Peer Wire Protocol. בשפות עם טיפוסיות חמורה יותר (Java),
   מניפולציה כזו דורשת יותר boilerplate.
3. **Flask להפעלה מהירה של REST**: ספרייה בוגרת ופשוטה ליצירת
   שרת HTTP מקומי.
4. **מהירות פיתוח**: Python מאפשרת איטרציה מהירה — חשוב במיוחד
   בשלבי אבחון של באגי רשת מורכבים (כמו באג ה-Stalling).
5. **ספרייה עשירה ל-cryptography ול-networking**: `hashlib`,
   `socket`, `struct`, `aiohttp` הם חלק מ-stdlib או מובנים.

### 9.5.2 למה Java ב-GUI?

Java נבחרה ל-GUI מסיבות מצטברות:

1. **דרישת השפה המהודרת**: סעיף 8(ב) במחוון מחייב לפחות שפה
   מהודרת אחת. Java נמצאת ברשימה המפורשת של שפות מהודרות.
2. **Swing — framework בוגר ל-Desktop GUI**: Swing קיים מ-1998
   ואיש Java רב-ניסיון יכול לכתוב Swing יעיל. הוא רב-פלטפורמתי
   (Windows, macOS, Linux).
3. **`java.net.http.HttpClient`**: ספרייה native ל-HTTP מ-JDK 11
   ואילך, ללא צורך בתלויות חיצוניות (כמו Apache HttpClient).
4. **טיפוסיות חזקה**: לאחר שתסכים על חוזה ה-API, Java מאפשרת
   מודלים מובהקים (POJOs כמו `TorrentStatus`) שמהדר תופס שגיאות
   הקלדה מוקדם.
5. **`ScheduledExecutorService`**: כלי ל-polling סדיר ב-EDT־friendly,
   כפי שנדרש לעדכון התצוגה ב-2 שניות.

### 9.5.3 שילובים אלטרנטיביים שנשקלו ונדחו

- **Python + C#/.NET**: C# הוא אלטרנטיבה לגיטימית ל-Java. ההכרעה
  לטובת Java נשענת על: זמינות JDK חינמית בכל פלטפורמה, פחות
  תלות בכלים מסחריים (Visual Studio), והוצאה לפועל פשוטה דרך
  `javac` ו-`java`.
- **Python + JavaScript (Electron)**: יוצר Web app שאינו "Desktop
  אמיתי", ודורש Node.js כתלות נוספת.
- **Python + C++ (Qt)**: יותר מורכב מ-Swing, וזמני קומפילציה
  גבוהים יותר. Java בוחר על איזון "פשטות-טיפוסיות".

## 9.6 הצדקת בחירת פרוטוקול האינטגרציה (REST)

### 9.6.1 חלופות שנשקלו

לתקשורת בין Java GUI ל-Python engine, נשקלו ארבע חלופות:

| חלופה | יתרונות | חסרונות | החלטה |
|---|---|---|---|
| **REST API (HTTP+JSON)** | פשוט, תקני, debuggable, multi-language | Polling overhead, JSON parsing | **נבחר** |
| gRPC | מהיר, type-safe (Protobuf), streaming | תלות בכלי-בנייה, מורכב לסטודנט | נדחה |
| WebSocket | push-based, real-time | סנכרון מורכב, אין HTTP semantics נטיביים | נדחה |
| Unix socket / Named pipe | קל מאוד, מקומי | פלטפורמה-תלוי, אין debug ב-curl | נדחה |

### 9.6.2 הצדקת REST

- **פשטות**: REST + JSON הוא הסטנדרט המקובל ב-2025 ל-API.
- **שקיפות**: כל בקשה ניתנת לבדיקה ב-`curl` או ב-Postman, ללא
  כלים מיוחדים.
- **Loose coupling**: Java GUI ו-Python engine יכולים להתפתח
  בנפרד — שינוי בייצוג פנימי בצד אחד לא משבית את השני, כל עוד
  ה-JSON נשמר.
- **Polling פשוט**: עבור עדכוני סטטוס שמהירותם בגרעיניות של 2
  שניות, polling מספיק. לעדכוני log נדרש קצב מהיר יותר — נפתר
  ע"י incremental polling עם sequence numbers (פרק 4.4.2).
- **תאימות עתידית**: ה-API ניתן לחשיפה לכלי-צד-שלישי (CLI,
  סקריפטים, GUI חלופי) בעתיד.

## 9.7 עקרונות תכן מנחים בחלופה הנבחרת

החלופה הנבחרת אינה רק "Python + Java + REST" — היא נשענת על שמונה
עקרונות תכן מנחים שייושמו לכל אורך הפרויקט:

1. **Single Responsibility Principle (SRP)** — לכל מודול אחריות
   אחת. `bencode.py` מקודד; `tracker_client.py` מתקשר עם trackers;
   `piece_manager.py` מנהל pieces.
2. **Separation of Concerns** — שכבות נפרדות: Network, Business
   Logic, API, Persistence, Presentation.
3. **Loose Coupling, High Cohesion** — מודולים מתקשרים דרך
   ממשקים מוגדרים; קוהזיה גבוהה בתוך כל מודול.
4. **Fail Fast** — בדיקות וולידציה מוקדמות; שגיאות חמורות
   מסתיימות בניתוק מיידי.
5. **Idempotency** — פעולות `POST /torrents/<id>/pause` ניתנות
   לקרוא פעמיים בלי השלכות.
6. **Observability** — מערכת log אחידה עם sequence numbers,
   טבלת events ב-SQLite.
7. **Defensive Programming** — timeouts בכל מקום, אכיפת גודל
   הודעה, ניתוק peers זדוניים.
8. **Test First** — bdiקות יחידה ל-8 מודולים, בדיקות אינטגרציה
   ל-API.

עקרונות אלה ייעשו ל-checkpoints בכל פרקי המימוש (11, 15, 21).
